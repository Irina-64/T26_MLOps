
# Правила совместной работы

## 1. Организация работы

Все участники работают через собственные форки репозитория `haiksarg/T26_MLOps`.

Схема внесения изменений:

1. Создание рабочей ветки в собственном форке.
2. Создание Pull Request в ветку участника (`adreyil` или `mourberg`).
3. Проверка изменений Release lead (@haiksarg).
4. Создание Pull Request из ветки участника в `main`.
5. Повторная проверка и объединение изменений в `main`.

Распределение ответственности:

- @haiksarg — Release lead, администрирование репозитория, управление задачами и правилами веток.
- @icy07 — окружение, Python, CI, тестирование и контроль качества.
- @Sheremgato — документация проекта, ADR, CODEOWNERS и анализ рисков.

## 2. Правила именования веток

Формат: `<тип>/issue-<номер>-<описание>`

Допустимые типы:
- `feat` — новая функциональность;
- `fix` — исправление ошибок;
- `docs` — документация;
- `ci` — изменения CI;
- `chore` — организационные изменения.

Пример: `docs/issue-3-adr-contributing-codeowners`.

## 3. Правила коммитов

Формат: `тип: краткое описание`.

Примеры:

- `docs: add project boundaries ADR`
- `fix: correct metric calculation`
- `ci: update quality checks`

Один коммит должен содержать одно логическое изменение.

Перед коммитом необходимо проверить `git status` и `git diff`.

Добавление файлов через `git add .` без предварительной проверки не допускается.

## 4. Pull Request

Каждый PR должен содержать:

- Ссылку на связанную issue.
- Описание выполненных изменений.
- Инструкцию по проверке.
- Результаты Ruff и pytest.
- Подтверждение отсутствия секретов и закрытых данных.

Для PR из форка в ветку участника используется `Refs #N`.

Для PR в `main` используется `Closes #N`.

Перед объединением изменений проверка CI `quality` должна завершиться успешно.

## 5. Code Review

Автор изменений не может одобрять собственный PR.

Reviewer обязан:

1. Просмотреть весь diff.
2. Проверить соответствие требованиям issue.
3. Оставить конкретные замечания при обнаружении проблем.
4. Повторно проверить изменения после исправлений.
5. Убедиться, что все обсуждения закрыты до merge.

Основной reviewer PR участников — @haiksarg.

Распределение ответственности фиксируется в CODEOWNERS.

Поскольку участники не являются коллабораторами основного репозитория, GitHub может не назначать их автоматически как CODEOWNERS. Поэтому review назначается вручную.

## 6. Правила защиты main

Для ветки `main` действует ruleset `main-protection`.

Установлены следующие требования:

- Изменения вносятся только через Pull Request.
- Требуется минимум одно одобрение другого участника.
- Новые коммиты сбрасывают устаревшие одобрения.
- Все обсуждения должны быть разрешены.
- Обязательная проверка CI — `quality`.
- Запрещены force push и удаление защищенной ветки.
- Разрешен только merge commit; squash и rebase merge отключены.

Ветки `adreyil` и `mourberg` также защищены от удаления и force push.

### Исключение 1. Одобрение PR администратора

Участники работают через форки и не имеют прав записи в основной репозиторий.

GitHub засчитывает обязательные одобрения только от пользователей с необходимыми правами.

Поэтому @haiksarg имеет право обхода требования одобрения в режиме Pull Request.

При этом прямой push в `main` не разрешается.

Перед объединением собственного PR администратор должен получить review другого участника и успешный результат проверки `quality`.

### Исключение 2. Одобрение последнего push

Правило `require_last_push_approval` отключено.

Причина: изменения проходят два PR, а последний merge commit в промежуточную ветку создает Release lead. При включенном правиле он не смог бы одобрить последующий PR в `main`.

Вместо этого Release lead проверяет оба PR и подтверждает, что содержимое второго соответствует уже проверенному первому PR.

## 7. Безопасность

Запрещается добавлять в репозиторий:

- Пароли, токены и ключи доступа.
- Файлы `.env`, содержащие секреты.
- Закрытые наборы данных.
- Большие модели и артефакты обучения.
- Виртуальные окружения и кэши.

Если секрет случайно попал в историю Git, необходимо немедленно отозвать его и заменить новым.

Удаление файла из последнего коммита недостаточно, поскольку секрет может остаться в истории репозитория.
