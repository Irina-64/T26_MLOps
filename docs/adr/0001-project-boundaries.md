
# ADR 0001: Границы учебного проекта

## Статус

Принято

Дата: 2026-10-08

Участники: @haiksarg, @icy07, @Sheremgato

## Контекст

Команда разрабатывает учебную MLOps-систему для прогнозирования стоимости жилья (Housing Price Prediction).

Необходимо определить границы проекта, требования к данным, критерии качества, состав системы и основные риски, чтобы участники использовали единый подход при выполнении следующих лабораторных работ.

## Решение


### Задача и пользователь

Разработать ML-систему для прогнозирования медианной стоимости жилья в районе на основании его характеристик.

Предполагаемый пользователь — аналитик агентства недвижимости, который получает через REST API ориентировочную оценку стоимости жилья для сравнительного анализа районов.

Система предназначена для демонстрации MLOps-процессов и не является инструментом профессиональной оценки стоимости конкретных объектов недвижимости.


### Входные данные

В качестве источника выбирается публичный датасет California Housing.

Датасет содержит характеристики географических районов Калифорнии: местоположение, средний доход, возраст зданий и другие признаки. Целевая переменная — медианная стоимость жилья в районе.

Исходные данные загружаются из открытого источника. Закрытые наборы данных и большие файлы не сохраняются в Git.

Вопрос версионирования данных с использованием DVC рассматривается в ЛР2.

### Метрики качества и эксплуатации

Основная метрика качества — RMSE (Root Mean Squared Error).

Реализация метрики уже находится в `src/housing_price/metrics.py`.

RMSE измеряет величину ошибок прогноза с повышенным штрафом за большие отклонения. Чем меньше RMSE, тем точнее прогнозы.

Метрика рассчитывается на отдельной тестовой выборке, которая не используется при обучении.

Эксплуатационная метрика — время ответа API на запрос прогноза. Планируется отслеживать p95 времени ответа и количество ошибок.

### Компоненты итогового проекта

В итоговую систему включаются:

1. Pipeline загрузки и обработки данных.
2. Модуль обучения ML-модели.
3. Модуль оценки качества прогнозов.
4. MLflow для отслеживания экспериментов.
5. REST API для получения прогнозов.
6. Docker для развертывания системы.
7. Мониторинг качества модели и работы сервиса.

Компоненты реализуются последовательно в следующих лабораторных работах.

### Основные риски

| Риск | Как обнаруживается | Меры |
|---|---|---|
| Некачественные данные | Пропуски, дубликаты, аномальные значения, изменение структуры данных | Проверка и валидация данных перед обучением |
| Невоспроизводимость результатов | Повторное обучение при одинаковых условиях дает существенно отличающиеся результаты | Фиксация зависимостей, random seed, параметров и версий данных |
| Проблемы эксплуатации | Увеличение времени ответа API, ошибки запросов, недоступность сервиса | Логирование, мониторинг задержек и ошибок, проверка доступности API |

### Отложенные решения

В рамках ЛР1 не реализуются:

- Версионирование данных через DVC — переносится в ЛР2.
- Выбор окончательной архитектуры ML-модели — после первых экспериментов.
- Определение конкретных порогов времени ответа и мониторинга — после реализации API и измерения производительности.

## Последствия

Принятые решения задают единые границы разработки и критерии оценки результата.

Использование публичного набора данных упрощает воспроизводимость проекта и исключает необходимость размещения закрытых данных в репозитории.

Основной метрикой качества становится RMSE, что позволяет сравнивать результаты экспериментов по единому критерию.

Применение MLflow, Docker и API позволит продемонстрировать полный жизненный цикл ML-системы.

Ограничение: California Housing содержит агрегированные данные по районам, поэтому результаты модели не подходят для определения стоимости конкретной квартиры или дома.

Отложенные решения будут уточняться в следующих лабораторных работах.
